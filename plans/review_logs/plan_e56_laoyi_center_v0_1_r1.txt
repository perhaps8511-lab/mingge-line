### 0.2 relay 既有七路由模式(workers/mingge-relay/worker.js)
七路由:`GET /history`、`GET /log`、`GET /study`、`POST /log/seal`、`POST /trace`、`POST /trigger/deepdive`、`POST /trigger/fupan`,加上根路徑 `POST /`(起卦主閘)。POST 類路由共同骨架(以 `/trigger/deepdive` 第 403-502 行為範本):
1. `Content-Type: application/json` 檢查

3. `X-Line-AccessToken` header 必帶,缺回 401
4. `resolveUserId(accessToken, LINE_CHANNEL_ID)`(第 654-677 行):先 `GET https://api.line.me/oauth2/v2.1/verify?access_token=...` 驗 token 有效且 `client_id===LINE_CHANNEL_ID`,再 `GET https://api.line.me/v2/profile`(帶 `Authorization: Bearer <token>`)取 `userId`/`displayName`。驗證失敗回 401。
5. payload 欄位白名單檢查(多餘欄位直接 400)
6. 業務邏輯 → 轉發下游(webhook 或未來的 Dify)
7. 統一用 `json(obj, status)` 輔助函式回應,CORS 由 `corsHeaders()` 處理

沒有任何既有路由呼叫過 Dify API(`grep -i dify` 零命中)── `/laoyi/chat` 是本 repo第一個 Dify 直連路由,呼叫慣例需自訂,採 Dify 官方 `chat-messages` blocking 端點慣例(`POST https://api.dify.ai/v1/chat-messages`,`Authorization: Bearer <app_key>`,body `{inputs:{}, query, response_mode:"blocking", user, conversation_id}`,回應含 `answer`/`conversation_id`)。

## 2. C2 — worker.js 新路由 `POST /laoyi/chat`

插入位置:緊接 `/trigger/fupan` 區塊之後(第 567 行 `}` 後)、`POST /` 主閘(第 569 行)之前,維持既有路由由上而下比對的順序慣例。

```js
if (request.method === "POST" && url.pathname === "/laoyi/chat") {
  const contentType = request.headers.get("Content-Type") || "";
  if (!contentType.toLowerCase().includes("application/json")) {
    return json({ error: "Bad JSON body" }, 400);
  }
  let payload;
  try { payload = await request.json(); }
  catch (e) { return json({ error: "Bad JSON body" }, 400); }

  const accessToken = request.headers.get("X-Line-AccessToken");
  if (!accessToken) return json({ error: "Missing access token" }, 401);

  let verifiedUserId;
  try {
    ({ userId: verifiedUserId } = await resolveUserId(accessToken, LINE_CHANNEL_ID));
  } catch (e) {
    console.log("Laoyi chat access token validation failed", e.message || e);
    return json({ error: "Invalid access token" }, 401);
  }

  const payloadIsObject = payload && typeof payload === "object" && !Array.isArray(payload);
  const payloadKeys = payloadIsObject ? Object.keys(payload) : [];
  if (payloadKeys.some(k => k !== "query" && k !== "conversation_id")) {
    return json({ error: "Unexpected field in payload" }, 400);
  }

  const rawQuery = payloadIsObject ? payload.query : undefined;
  const query = typeof rawQuery === "string" ? rawQuery.trim() : "";
  if (!query || query.length > 2000) {
    return json({ error: "Invalid query" }, 400);
  }
  const rawConvId = payloadIsObject ? payload.conversation_id : undefined;
  const conversationId = typeof rawConvId === "string" ? rawConvId.slice(0, 128) : "";

  if (!env.DIFY_LAOYI_KEY) {
    return json({ error: "DIFY_LAOYI_KEY not configured" }, 503);
  }

  let difyRes;
  try {
    difyRes = await fetch("https://api.dify.ai/v1/chat-messages", {
      method: "POST",
      headers: {
        "Content-Type": "application/json",
        "Authorization": "Bearer " + env.DIFY_LAOYI_KEY,
      },
      body: JSON.stringify({
        inputs: {},
        query,
        response_mode: "blocking",
        user: verifiedUserId,
        conversation_id: conversationId,
      }),
    });
  } catch (e) {
    console.log("Laoyi Dify forward failed", e.message || e);
    return json({ error: "Dify request failed" }, 502);
  }
  if (!difyRes.ok) {
    console.log("Laoyi Dify forward failed", difyRes.status);
    return json({ error: "Dify request failed" }, 502);
  }
  let difyData;
  try { difyData = await difyRes.json(); }
  catch (e) { return json({ error: "Dify response parse failed" }, 502); }

  return json({
    answer: typeof difyData.answer === "string" ? difyData.answer : "",
    conversation_id: typeof difyData.conversation_id === "string" ? difyData.conversation_id : "",
  }, 200);
}
```

**B2 標註**:`env.DIFY_LAOYI_KEY` 目前 Cloudflare Secrets 未貼(卡上明訂由 Perth 親貼)── 本路由施工時以此佔位變數名稱寫入代碼(不硬編任何金鑰字面值),缺鑰時路由回 503(`DIFY_LAOYI_KEY not configured`),不擋其他三件(C1/C3/C4)的施工與驗收。`wrangler.toml` 不需改(secret 不進 toml)。**待 Perth 執行 `wrangler secret put DIFY_LAOYI_KEY` 後,C2 才能真機通話驗收(卡驗收條件②)**。

**Stateless 落實**:整條路由不寫 Airtable、不寫 D1/KV,`conversation_id` 純粹是 Dify 自己維護的 session 概念,relay 只透傳、不留存 ── 卡「不落任何持久層」鐵則。

### 3.2 交給書僮(liff.sendMessages,比照既有 `studySendAskLaoyi` 錯誤處理慣例)
```js
async function laoyiHandoffToService(){
  var lastUserMsg = laoyiLastUserMessage() || '（TA 尚未輸入問題，直接請書僮協助）';

    if(typeof liff==='undefined'){ throw new Error('LIFF unavailable'); }
    await ensureLiffInit();
    if(!(liff.isInClient && liff.isInClient())){ throw new Error('not in LINE client'); }
```

   - 使 `initAskLaoyiPage()` 中止、頁面無法進場

   應直接使用 `contentId`，並限制長度。若真正需要二次編碼，必須把契約寫清楚並捕捉 decode 例外。

2. [BLOCKER] `content_id` 的資料契約自相矛盾  
   名稱叫 `content_id`，實際傳入「篇名」。這會造成後續把資料庫 ID、slug 或篇名混用。至少應二選一：

   - 改名 `content_title`
   - `content_id` 傳穩定 ID，前端再從 `/study` 查正式篇名

   現行方案還沒有長度上限、控制字元規則與不存在文章的處理。

3. [BLOCKER] deep-link 能力沒有任何正式入口接上，驗收①可能只是在測死碼  
   計畫刻意不改 `studySendAskLaoyi`，因此「拿這篇問老易」仍走舊 `sendMessages`，正常使用者旅程根本不會進入 S3。若 taskcard 的 deep link 是實際產品流程要求，只有人工拼 URL 不算完成。必須由卡明確裁決：

   - 本卡接上書房入口；或
   - 驗收明文允許本卡只提供路由能力，並列出後續卡與 owner

4. [BLOCKER] 對話送出存在並行競態，會破壞 Dify conversation  
   使用者可連點或連按 Enter。在第一輪尚未取得 `conversation_id` 前，第二輪也會以空 ID 發出，建立兩條 Dify conversation；回覆又可能倒序，最後回來的 response 會覆蓋 `laoyiConvId`。必須定義：

   - 單飛：請求完成前鎖 send/composer；或
   - 明確 queue，依序送出
   - 防 double-submit
   - 回覆順序與 conversation ID 更新規則

5. [BLOCKER] 25 輪計數語意錯誤  
   `laoyiTurnCount++` 放在 catch 後，因此 token 失效、503、網路失敗也算一輪；第 25 輪後每次又會反覆執行 `laoyiShowClosing()`，可能產生重複按鈕。需定義「一輪」是成功的 user–assistant exchange，並讓 closing render idempotent。

6. [BLOCKER] E47「段落 ≤4 行」沒有實作，也無法驗收  
   「對話體天然短句」不是控制機制。Dify 回覆長度完全不受前端掌控，螢幕寬度與字級也會改變實際行數。目前斷言表沒有測此條，與「E47 五條」驗收宣稱不符。需明確採用可驗證方案，例如分段／摘要摺疊／最大可視行數加展開，並以目標 viewport 做 DOM 渲染測試。

7. [BLOCKER] 客服 fallback 所依賴的 DOM 在新 DOM 規格中不存在  
   `laoyiHandoffToService()` 呼叫：

   ```js
   showAskLaoyiFallback(lastUserMsg,'askLaoyiStatus','askLaoyiFallback','askLaoyiFallbackText')
   ```

   但 1.1 的重寫 DOM 沒列出這三個元素。若舊 `#page-about` 被取代，它們很可能一起消失，fallback 將無法顯示，甚至在 helper 未做 null 防禦時二次拋錯。必須保留對應 DOM，或設計問答室專用 fallback。

8. [BLOCKER] 「原句送出」在沒有 user message 時被違反  
   計畫會送：

   ```text
   （TA 尚未輸入問題，直接請書僮協助）
   ```

   這不是 TA 原句，卻會作為 TA 訊息進 OA。應在沒有原句時禁止送出、要求先輸入，或提供獨立客服輸入框；不能替使用者發明內容。

9. [BLOCKER] 「最後一則 user message」不等於「客服題原句」  
   常駐入口可在任意時點按下，因此可能把上一個易經問題、健康資訊或其他敏感內容送往書僮鏈。這不符合「客服題原句」契約，也造成非預期資料轉送。必須把 handoff 綁定到明確選取的訊息，或在送出前顯示內容並讓使用者確認。

10. [BLOCKER] 書僮交接缺少防重複與狀態控制  
    重複點「店務找書僮」會反覆插入 S5 和新按鈕；連點「交給書僮」會重複呼叫 `sendMessages`，可能在 OA 建立多筆相同事件。需要 busy/disabled 狀態、成功後不可重送，並讓 S5/CTA 建立具冪等性。

11. [BLOCKER] S6 對下游成功狀態作了未經證實的承諾  
    `liff.sendMessages()` 成功只代表訊息送進 LINE 對話，不代表 5379670 已接收、成功分流或「書僮接著答」。若 S6 是卡上已定稿文字，驗收必須包含下游真機結果；否則這句會把 transport success 說成 business success。

12. [BLOCKER] Dify route 沒有 timeout，blocking request 可無限拖住  
    Worker 對 token verify、profile 與 Dify blocking 呼叫均未定義 timeout。Dify 卡住時前端 typing bubble 會長時間不結束，Worker 資源也被占用。需要 `AbortController` timeout，並區分 timeout 與其他 upstream failure。

13. [BLOCKER] 新付費端點沒有 rate limit／濫用邊界  
    任一有效 LINE access token 都可以無限制呼叫 blocking Dify API，且 query 可達 2000 字。這會形成成本與 DoS 入口。即使 stateless 禁止 D1/KV，也必須在計畫中明確裁決可接受的限制方式，例如 Cloudflare Rate Limiting、WAF 規則或既有 gateway 配額；不能完全不處理。

14. [BLOCKER] `conversation_id` 被靜默截斷，會改壞資料  
    `slice(0,128)` 會把不合法 ID 變成另一個 ID，再交給 Dify。應依 Dify 實際契約驗證格式和最大長度；超限回 400，不得靜默變造。非字串但有值也應回 400，而不是悄悄當新 conversation。

15. [BLOCKER] Dify 成功回應驗證不足  
    `answer` 或 `conversation_id` 缺失時，relay 仍回 200。前端甚至可能顯示自製的「老易暫時沒有回應」，把 upstream schema error 偽裝成正常對話。至少應驗證：

    - response 是 object
    - `answer` 是非空字串
    - `conversation_id` 是符合契約的非空字串
    - 回應大小在上限內

    不符應回 502，不能回成功。

16. [BLOCKER] 前端沒有 query 長度契約，會先顯示使用者泡泡再收到 400  
    Worker 限制 2000，但 textarea 沒 `maxlength`，`laoyiSend()` 也沒相同 validation。使用者輸入過長時，UI 先把內容當成功送出，再顯示泛化錯誤。前後端必須共享同一限制，並在送出前顯示具體錯誤。

17. [BLOCKER] S4 heuristic 無法符合「決策題收束」的一般驗收  
    regex 明知會漏判／誤判，且缺少大量自然說法，如「是否適合」「哪個比較好」「現在能不能」「A 還是 B」。若卡要求決策題均出現 CTA，這個實作無法通過。需要：

    - 由 Dify 回傳結構化旗標，但這涉及 prompt 契約及回歸；或
    - 明確限縮 taskcard 的可驗收語句集合，並以 fixtures 鎖定

    「plan 自訂」不能取代可測資料契約。

18. [BLOCKER] 驗收②的「前端無端點」與實作矛盾  
    前端必須持有 relay URL；表格卻寫「前端無端點/金鑰」，斷言又只 grep `dify.ai`。應改成精確契約：「前端可含 relay endpoint，不得含 Dify endpoint 或 Dify key」。否則驗收文字與實作互相衝突。

19. [BLOCKER] CORS/OPTIONS 契約沒有納入新自訂 header 驗收  
    使用 `X-Line-AccessToken` 會觸發 preflight。不能只說沿用 `corsHeaders()`；必須驗證 `Access-Control-Allow-Headers` 確實包含 `Content-Type, X-Line-AccessToken`，且 `OPTIONS /laoyi/chat` 能成功。否則瀏覽器會在路由前攔掉請求。

20. [BLOCKER] 測試計畫不足以驗證主要失敗路徑  
    Worker 至少缺以下測例：

    - JSON scalar／array／null
    - 缺 query、非字串 query、純空白、超長 query
    - `conversation_id` 非字串／超長／非法格式
    - token 缺失、verify 失敗、channel mismatch、profile 失敗
    - secret 缺失
    - Dify timeout、network error、非 2xx、非 JSON、空 answer、缺 conversation ID
    - CORS preflight
    - 連續送出與回覆倒序
    - handoff double-click／無 user message／sendMessages failure
    - malformed deep link、超長篇名
    - IME composition 下按 Enter 不可誤送

    現有「DOM 抽取／payload 驗證／文案比對」不足以證明驗收成立。

21. [SUGGEST] `RELAY_URL+'laoyi/chat'` 有 slash 契約風險  
    若 `RELAY_URL` 不以 `/` 結尾會組成錯誤 URL；若以 `/` 結尾才正確。建議使用 `new URL('/laoyi/chat', RELAY_URL)` 或共用 URL builder。

22. [SUGGEST] 必須明訂 bubble 使用 `textContent`  
    `contentTitle`、query、Dify answer 都是不可信文字。計畫只說「純文字氣泡」，應在實作與測試中鎖定不得使用 `innerHTML`。

23. [SUGGEST] Enter 行為需處理熟齡輸入與 IME  
    建議明訂 Enter 送出、Shift+Enter 換行，且 `event.isComposing` 或 keyCode 229 時不得送出，避免中文選字被當成提交。

24. [SUGGEST] `initAskLaoyiPage()` 應可重入  
    若 SPA 路由反覆進入 `#page-about`，目前可能重複掛 listener、重複開場泡泡。建議設初始化旗標，或先移除 listener／清理 thread，並定義返回格5時是延續當頁 conversation 還是重置。

25. [SUGGEST] Dify 第三方資料傳輸需列入資料邊界  
    `verifiedUserId` 與使用者全文會送至 Dify。即使不寫 Airtable/D1/KV，也不等於「不持久化」；Dify 可能保存 conversation/log。應在 stateless 宣稱中明確區分「relay 不落地」和「Dify 端保存政策」，並確認告知／隱私基準。

26. [SUGGEST] 錯誤回應應提供穩定 error code  
    UI 現在只能看到 HTTP status。建議 worker 回 `code`，例如 `INVALID_QUERY`、`UPSTREAM_TIMEOUT`、`UPSTREAM_SCHEMA_ERROR`，前端只顯示安全、可理解的分類訊息，不暴露內部設定名稱。
